彈珠賽事影像判定Marble Race Result Judging

2024 – 2026
PythonYOLORoboflowPyTorchOpenCVONNXFastAPIPyQt5

用影像辨識即時判定彈珠賽事的落球排名，取代人工判讀。已上線運行。Real-time ranking for marble races from video, replacing manual reading of the result. In production.

  • 以 Roboflow 標註並訓練 YOLO 模型，把每顆球訓練成獨立 class，排名系統就能直接用 class 辨識球體，繞過多物件追蹤的 ID switch 問題。
  • 落球判定做成四狀態機。關鍵決定是所有 threshold 都用秒、不用 frame 數——YOLO 推論的 fps 會隨負載浮動，拿 frame 數當基準遲早會漂掉。
  • 二段時間確認用來容忍偶發的漏偵測，存活時間 threshold 濾掉開局瞬間的雜訊誤判，另有 stale 機制清除 ghost track。
  • 排名依據取「最後一次被偵測到的時間」而不是確認落球的時刻，確認延遲才不會影響排名的公平性。
  • 對外以 FastAPI 提供賽果查詢，現場操作介面用 PyQt5；推論放在獨立 thread，避免卡住 UI。
  • Labelled and trained a YOLO model in Roboflow, with each ball as its own class. The ranking system can then identify a ball directly by class, sidestepping the ID-switch problem in multi-object tracking.
  • Drop detection is a four-state machine. The key decision was to express every threshold in seconds rather than frames — inference fps drifts with load, so a frame-based threshold will eventually misjudge.
  • A two-stage time confirmation absorbs occasional missed detections, a survival threshold filters out noise at the start of a round, and a stale rule clears ghost tracks.
  • Ranking uses the time a ball was last seen, not the moment the drop was confirmed, so confirmation latency doesn't distort the result.
  • Results are served over FastAPI, with a PyQt5 interface for staff on site. Inference runs on its own thread so the UI stays responsive.

                          再消失一段時間 → 確認落球 ──▶ DROPPED

ACTIVE ──消失過久──▶ 清除（ghost track）
Threshold防的是什麼
判定線位置只有越線的球才進入落球判定流程
消失時間（進 CONFIRMING）容忍 YOLO 偶發漏偵測，消失一下不算落球
確認時間二段確認，再等一段時間才判定成立
存活時間 threshold過濾開局瞬間的誤判，雜訊不會佔到名次
stale 時間清除長時間沒再出現的 ghost track

這套判定邏輯的前提是「模型一定會錯」。與其追求更高的辨識率，不如讓下游邏輯能吸收錯誤——漏偵測用時間容忍，誤判用存活 threshold 濾掉，兩種失效方式分開處理。

ACTIVE ──crosses the line──▶ PENDING ──gone a while──▶ CONFIRMING
                                                           │
                            gone again → drop confirmed ──▶ DROPPED

ACTIVE ──gone too long──▶ cleared (ghost track)
ThresholdWhat it guards against
Line positionOnly a ball past the line enters the elimination flow
Disappearance time (into CONFIRMING)Occasional missed detections — briefly gone isn't a drop
Confirmation timeA second stage before the drop is taken as final
Survival thresholdFalse positives at the start of a round taking a rank
Stale timeGhost tracks that never reappear

The whole design assumes the model will be wrong. Rather than chase a higher detection rate, it lets the downstream logic absorb errors: time tolerance for missed detections, a survival threshold for false ones, each failure mode handled separately.

租約與調度的實作細節How the lease and scheduling work

租約的三段 Lua script

Key 是 table-client:lease:{遊戲類型}:{桌號}，value 存 podId，所以每張桌各自有一個 owner 標記。三個操作都必須先確認 owner 是自己：

acquire  value 已是自己      → 續期
         key 不存在         → SET PX 搶下
         其他               → 回 0，不搶別人的

renew    owner 相符才 pexpire

release  owner 相符才 del

拆成 GET 再 SET 或 DEL 的話，兩個動作之間有空窗，可能覆寫掉別人剛搶到的租約。放進 Lua 讓判斷與寫入變成一個原子操作。

Supervisor 每輪掃描做的事

worker 存在但沒在跑  → 回收舊實例
worker 不存在        → 搶租約；搶到才建 worker
                       建立失敗要 rollback：
                       dispose scope + 釋放租約
worker 存在          → 續租；失敗就停掉 worker

最後一條是刻意的取捨：租約失效代表這張桌的所有權可能已經被別人拿走，繼續操作的風險遠高於短暫停擺。關閉時統一釋放所有 worker、scope 與租約，支援 graceful shutdown。

狀態機

桌台共 10 種狀態，factory 明確處理其中 7 種，其餘連同未定義值一律落進錯誤復原分支。整個系統只有這一處 switch，新增狀態只要改一個地方。

The three Lua scripts

The key is table-client:lease:{gameKind}:{tableNumber} and the value holds the pod id, so every table carries its own owner marker. All three operations check ownership first:

acquire  value already mine  → extend
         key missing         → SET PX to claim
         otherwise           → return 0, never steal

renew    pexpire only if the owner matches

release  del only if the owner matches

Split into GET then SET or DEL, there is a window between the two calls where you can overwrite a lease someone else has just claimed. Inside Lua the check and the write are one atomic step.

What the supervisor does each pass

worker exists but stopped → reclaim the old instance
no worker                → try the lease; build only on success
                            on failure roll back:
                            dispose scope + release lease
worker running           → renew; on failure stop the worker

That last line is a deliberate trade-off. A lost lease means ownership may already have moved elsewhere, and carrying on is far riskier than a brief gap. On shutdown every worker, scope and lease is released together.

State machine

There are ten table states. The factory handles seven explicitly; everything else, including undefined values, falls into error recovery. It's the only switch on that enum in the codebase, so adding a state means touching one place.

  • The faster option was to extend the existing audit_logs table. I built a separate operation_logs table instead — roughly double the effort, in exchange for keeping business meaning fully apart from raw HTTP logs and leaving the existing pipeline untouched.
  • Writes go through a Redis stream and a consumer group before landing in ClickHouse, so auditing never slows the main request. The table is MergeTree, partitioned by day, with a TTL for expiry.
  • Middleware supplies the HTTP-level meaning (role, menu, operation type); the service layer supplies before/after state snapshots. Both paths meet in the same stream and are merged on write.
  • OperationType and Menu are closed types implementing encoding.TextUnmarshaler. One implementation guards both Gin form binding and the stream consumer, so an invalid value returns 400 instead of quietly yielding an empty result set.
  • The query window ran into a timezone problem: QA could query a given day, but the early-morning hours of it were rejected. The frontend counted back from local midnight while the backend ran on UTC — nearly a full day apart. I kept business timezones out of the backend, left it a loose backstop with an extra day of slack, and let the frontend enforce the precise boundary.
  • Snapshots first stored raw enum values and resource IDs. I changed all of them to role and resource names — the people reading an audit trail are auditors, and role=3 means nothing to them.
架構與那個時區決策Architecture, and that timezone call

兩條寫入路徑

HTTP 請求
   ↓
operation_log middleware
   讀 JWT / RBAC     → 角色
   依路由推導        → 操作類型、選單
   GET 白名單命中    → 查詢條件寫入 before_state
   ↓
Redis Stream ──── Service 層 CUD 方法
   │                 操作前查詢 → before_state
   │                 操作後查詢 → after_state
   ↓
Consumer Group → ClickHouse operation_logs

Middleware 拿不到業務 snapshot，Service 層拿不到 HTTP context，所以拆兩條路徑各自蒐集，再於 Stream 匯流。

為什麼時區界線交給前端

需求是「可查最近 N 天」。後端跑 UTC，前端在 UTC+8 以當地當天 00:00 往回推算，兩者最多差將近一天，結果邊界那天的凌晨時段會被後端誤擋——這是 QA 實際回報的 bug。

要在後端做精準判斷，就得把業務時區帶進後端邏輯。我選擇不這樣做：後端只做寬鬆的 backstop、多留一天緩衝吸收落差，精準的使用者體驗界線由前端負責。代價是後端實際可查的範圍比需求多一天，但換到的是後端保持時區無關。

記錄粒度

稽核紀錄記太少沒用，記太多等於沒記。GET 端點採白名單，只有命中的才記；前端自動輪詢可帶一個 header 略過記錄，避免列表刷新把有價值的紀錄洗掉。

Two write paths

HTTP request
   ↓
operation_log middleware
   read JWT / RBAC      → role
   derive from route    → operation type, menu
   whitelisted GET      → query terms into before_state
   ↓
Redis Stream ──── service-layer CUD methods
   │                 query before  → before_state
   │                 query after   → after_state
   ↓
consumer group → ClickHouse operation_logs

Middleware can't see business snapshots and the service layer can't see HTTP context, so each path collects what it can and they merge in the stream.

Why the frontend owns the timezone boundary

The requirement was "queryable for the last N days". The backend runs UTC; the frontend counts back from local midnight in UTC+8. Up to nearly a day apart, which meant the early hours of the boundary day were rejected — a bug QA actually filed.

Judging it precisely on the backend would mean pulling a business timezone into backend logic. I chose not to: the backend keeps a loose backstop with a day of slack, and the frontend owns the precise boundary. The cost is that the backend will serve a day more than the requirement; the gain is a backend that stays timezone-agnostic.

How much to record

Record too little and an audit trail is useless; record everything and it may as well be. GET endpoints are whitelisted, and the frontend's automatic polling can pass a header to skip logging, so list refreshes don't flush out the entries that matter.

控制 8 條實體賽道（含一條實體測試賽道）的自動化系統，從硬體驅動到 Web 監控介面由我獨立開發。除了控制軟體，也寫韌體、跟外部廠商一起討論電路板設計、做基礎焊接。The automation system driving eight physical tracks (one of them a physical test track), built solo from the hardware drivers up to the web monitor. Alongside the control software I wrote firmware, worked with an external vendor on the board design, and did the basic soldering.

  • 硬體抽象層以 SPI 驅動 MCP23S17 I/O Expander，讀取最多 28 路光學感測器，並自動偵測新舊兩代感測板，讓同一份程式碼吃兩種硬體。
  • RF 閘門驅動是最難的一塊，實體環境什麼都會壞，所以疊了六層防禦（展開看細節）。
  • 賽道流程用 Strategy 加 Factory，8 條賽道各有自己的開賽條件與結束判定，新增一條只要加一個 flow 並註冊，不動主控迴圈。
  • 偵測不到硬體時自動退回模擬模式，開發者在沒有 SPI 的 Mac 上也能跑完整流程。
  • 依賽事事件切換 OBS 場景，把遊戲邏輯與直播導播串起來。三支程式分別以 systemd 常駐，監控介面掛掉不會影響賽道控制。
  • The hardware layer drives an MCP23S17 I/O expander over SPI to read up to 28 optical sensors, and detects which of two sensor-board generations is present so one codebase serves both.
  • The RF gate driver was the hard part. In a physical setting everything fails eventually, so it ended up with six layers of defence (details below).
  • Track flows use strategy plus factory: each of the eight tracks has its own start conditions and finish rules, and adding one means adding a flow and registering it, without touching the main loop.
  • When no hardware is detected it falls back to a simulation mode, so a developer on a Mac with no SPI can still run the whole flow.
  • OBS scenes switch on race events, tying game logic to the broadcast. Three processes run under systemd, so losing the monitor UI doesn't affect track control.

雙代感測板自動偵測

舊板一顆晶片 12 路感測器，新板兩顆 28 路。兩顆晶片的硬體位址都是 0，靠獨立的 chip select 區分。程式先建第一顆，再嘗試建第二顆並標記是否存在，感測器數量上限隨偵測結果決定，所以舊賽道不需要維護另一個分支。

Every layer maps to something that actually happened, not something imagined up front. It's also why I now pay attention to failure paths in services — a physical setup finds plenty of ways to show you that optimistic assumptions don't hold.

Detecting two sensor-board generations

The older board has one chip and 12 sensors; the newer one has two chips and 28. Both chips sit at hardware address 0 and are told apart by separate chip-select lines. The code brings up the first chip, tries the second and records whether it answered, and the sensor limit follows from that — so older tracks don't need a separate branch.
